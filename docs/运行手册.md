# 运行手册

面向"把这套系统跑起来、跑对、出问题知道往哪看"的场景。
第一次上手先看仓库根目录 [README](../README.md) 的《快速开始》，本手册补充细节与排错。

---

## 1. 三个进程与端口

系统由三个进程组成，互相独立启动，**启动顺序不影响**（后端连不上分析服务时会自动降级，见 §6.4）。

| 进程 | 技术 | 默认端口 | 地址 |
| --- | --- | --- | --- |
| 后端 | Spring Boot | 9090 | http://localhost:9090 |
| 前端（开发服务器） | Vite | 5173 | http://localhost:5173 |
| 分析服务 | FastAPI（Docker） | 8000 | 仅绑定 127.0.0.1 |

依赖的外部资源：MySQL 8（3306）、Docker（跑分析服务与集成测试）。

### 环境要求

| 组件 | 版本 | 用途 |
| --- | --- | --- |
| JDK | 17+ | 后端 |
| Maven | 3.8+ | 后端 |
| Node.js | 18+（CI 用 22） | 前端 |
| MySQL | 8.x | 数据库 |
| Docker | 20.10+ | 分析服务、后端集成测试 |

> 没有 Docker 时：前端与后端仍可正常开发，但 `mvn test` 里的集成测试会失败，
> 智能分析会一直走降级路径（规则模板）。

## 2. 最短启动路径

```powershell
# 1) 数据库（只做一次）
#    Flyway 会建表，但不会建库
mysql -uroot -p -e "CREATE DATABASE IF NOT EXISTS asset_management DEFAULT CHARACTER SET utf8mb4 COLLATE utf8mb4_general_ci;"

# 2) 凭据（二选一：环境变量 或 back-end/.env）
$env:DB_PASSWORD = "你的MySQL密码"
$env:JWT_SECRET  = "至少32字节的随机串"      # openssl rand -base64 48

# 3) 分析服务（可选，但"智能分析"要用）
cd llm-service
$env:DEEPSEEK_API_KEY = "sk-..."
docker compose up -d

# 4) 后端
cd ..\back-end
mvn spring-boot:run

# 5) 前端（另开一个终端）
cd ..\front-end
npm install
npm run dev
```

打开 http://localhost:5173，用 `admin` / `123456` 登录（演示账号见 README）。

## 3. 后端启动细节

### 3.1 凭据从哪里来

优先级：**系统环境变量 > `back-end/.env` > `application.yml` 默认值**。

`back-end/.env` 会被自动加载（`spring.config.import: optional:file:./.env[.properties]`），
已被 `.gitignore` 忽略。注意它按 **properties** 解析，不是 dotenv：

- 不能写 `export KEY=`
- 值不能加引号
- 值里不能有 `${}`

`JWT_SECRET` 缺失或不足 32 字节时，`JwtUtils.validateSecret()` 会让应用**启动即失败** ——
这是有意为之，不是 bug。

### 3.2 换端口

```powershell
mvn -o -B -DskipTests spring-boot:run "-Dspring-boot.run.arguments=--server.port=18888"
```

端口被占用、或环境里注入了 `SERVER_PORT` 时用这个方式显式覆盖。
换了端口记得同步改前端 `vite.config.ts` 里 `/api` 的 proxy target。

### 3.3 数据库迁移

Flyway 在启动时自动执行 `src/main/resources/db/migration/V*.sql`，当前到 **V13**。

> ⚠️ **迁移文件一旦被 apply 过，绝不能原地编辑。**
> Flyway 把文件内容的 CRC32 记为 checksum，改一个注释字符都会导致 checksum 变化，
> 任何跑过该版本的库启动时 validate 失败，直接 `APPLICATION FAILED TO START`。
> 要补充说明请新增 `V(n+1)`，或写进 Java 注释。
>
> ⚠️ **文件名必须双下划线**：`V13__desc.sql`。单下划线（`V13_desc.sql`）会被 Flyway
> **静默跳过**，只在启动日志里留一行 INFO，非常容易漏看。

## 4. 前端

```bash
npm install       # 首次
npm run dev       # 开发服务器，5173，/api 代理到 9090
npm run build     # vue-tsc 类型检查 + vite 打包
npm run test      # vitest 单元测试（32 个）
```

`npm run test` 只跑纯逻辑单测（路由守卫、轮询、格式化），不挂载组件，
因此不需要 jsdom / 浏览器。

## 5. 分析服务（llm-service）

### 5.1 启动

```bash
cd llm-service
docker compose up -d          # 常驻，restart: unless-stopped，开机自动拉起
docker compose logs -f        # 看日志
docker compose down           # 停止
```

不装 Docker 也可以直接跑：

```bash
D:\Python\python.exe -m uvicorn main:app --host 127.0.0.1 --port 8000
```

### 5.2 安全边界（重要）

容器内必须监听 `0.0.0.0` 才能被宿主访问，所以 Dockerfile 用的是 `--host 0.0.0.0`；
**对外暴露范围由端口映射限制在回环**：

```yaml
ports:
  - "127.0.0.1:8000:8000"     # 只有本机能访问
```

**不要**改成 `"8000:8000"` —— 这个服务没有鉴权，一旦映射到所有网卡，
同网段任何人都能调分析接口并消耗你的 API 额度。

API Key 通过宿主环境变量注入（`${DEEPSEEK_API_KEY}`），不写进镜像、不落盘。

### 5.3 没有 Key 会怎样

不会报错，会走**规则模板**降级：返回 `engine=rule`，前端在结果弹窗顶部显示
「分析服务当前不可用，以下结论由规则模板生成」。数据库里 `analysis_job.engine`
会记下真实来源，事后可查。

## 6. 测试

| 层 | 命令 | 数量 | 前提 |
| --- | --- | --- | --- |
| 后端 | `mvn -f back-end/pom.xml test` | 59（39 单测 + 20 集成） | **Docker**（集成测试起 mysql:8.0 容器） |
| 前端 | `cd front-end && npm run test` | 32 | 无 |
| 分析服务 | `cd llm-service && python -m pytest -q` | 26 | 无（不联网） |

后端测试分两类：**39 个 Mockito 单测**（不加载 Spring）、**20 个 Testcontainers 集成测试**
（真 MySQL）。集成测试会实际执行全部迁移脚本，所以**迁移写错 CI 会红** ——
这类问题单测拦不住，也是当初补集成测试的主要原因。

## 7. 分支模型与推送（容易踩）

仓库有两个互不相关的历史分支，远端分别是：

| 本地分支 | 远端 | 用途 |
| --- | --- | --- |
| `master` | `origin` → **Gitee** | 完整开发历史 |
| `public` | `github` → GitHub | 公开快照（干净历史） |

**⚠️ 绝不要把 `master` 推到 GitHub。** 初始提交里有旧版明文凭据，
推上去会让它重新进入公开历史。

日常流程：

```powershell
git push origin master                    # 推 Gitee
# 同步公开快照
git checkout public
git checkout master -- back-end front-end llm-service .github .gitignore
git add -A -- back-end front-end llm-service .github .gitignore
git commit -m "..."
git push github public:master             # 只推 public
git checkout master
```

`public` 与 `master` 是无关历史，不能用 `git merge`（要 `--allow-unrelated-histories`），
所以用上面的 checkout 方式同步。

## 8. CI

GitHub Actions，配置在 `.github/workflows/ci.yml`，三个并行 job：

| job | 内容 | 时长 |
| --- | --- | --- |
| 后端测试 | JDK 17 + `mvn test`（含 Testcontainers，会拉 mysql:8.0） | ~75s |
| 前端构建与测试 | Node 22 + `npm ci` + `npm run build` + `npm run test` | ~80s |
| llm-service 测试 | Python 3.13 + pytest | ~15s |

- **只有 GitHub 会跑 CI，Gitee 不会。** 推 Gitee 不代表验证过。
- 支持手动触发：仓库页 → Actions → 左侧 `CI` → 右上 `Run workflow`。
- 分支保护规则 `protect-master` 已启用：禁止删除 master、禁止强推。
  规则只作用于这两项，**正常快进推送不受影响**，也不需要 bypass 名单。
  如果以后要加 `Require status checks`，记得同时把 `Repository admin` 加进 bypass，
  否则会把自己的直接推送也挡掉。

## 9. 常见故障

### 9.1 后端启动即失败，报 JWT secret 相关

`JWT_SECRET` 没设或不足 32 字节。设一个 `openssl rand -base64 48` 的值。

### 9.2 启动失败，Flyway 报 checksum mismatch

有人改了已 apply 过的迁移文件。**不要用 `flyway repair`** ——
正确的做法是把文件按字节还原（或新增一个 V(n+1)），因为期间任何启动都会在
validate 阶段先挂，不会有库真的带着新 checksum。

### 9.3 迁移脚本没被执行

检查文件名是不是单下划线。`V13_add_x.sql` 会被**静默跳过**，
只在日志里留一行 `did not follow the filename convention`。

### 9.4 `mvn test` 报 "Could not find a valid Docker environment"

十有八九不是 Docker 没启动，而是 **API 版本协商**问题：

- Testcontainers 1.19.3 内置客户端按 API v1.32 请求
- 新版 Docker Engine 最低接受 1.40，直接拒绝（HTTP 400）
- 但对外表现是上面这句误导性的报错

`AbstractIntegrationTest` 里已用 `System.setProperty("api.version", "1.41")` 处理
（1.41 是 Docker 20.10 到 29 都接受的区间）。**已验证升到 Testcontainers 1.20.6
仍需要这段补丁**，所以不要为了删它去升版本。

若 CI 上显式设了 `DOCKER_API_VERSION`，代码会尊重它、不覆盖。

### 9.5 前端登录 401 / 接口全 404

- 401：后端没起，或 token 过期，清 localStorage 重新登录
- 404：`vite.config.ts` 的 proxy target 与后端实际端口不一致（默认 9090）

### 9.6 智能分析结果看起来像模板文案

说明分析服务没起或没配 Key。查：

```bash
docker ps | grep fams-llm-service        # 容器在不在
curl http://127.0.0.1:8000/health        # 服务活不活
```

也可以直接查库确认这批结论的来源：

```sql
SELECT id, task_id, status, engine, finished_time FROM analysis_job ORDER BY id DESC LIMIT 5;
```

`engine = llm` 是模型产出，`rule` 是模板兜底，`mixed` 是部分片失败。

### 9.7 分析接口报"排队已满"

后端线程池是核心 2 / 最大 4 / 队列 50。队列满时会拒绝并提示稍后重试 ——
这是设计行为，避免把 Tomcat 线程拖死。排队期间可稍等再点。

### 9.8 分析任务一直停在 RUNNING

后端进程在分析途中被杀会留下这种行。前端轮询有 200 秒上限，到点提示
「分析超时，请稍后重试」，不会无限等待。重新提交即可。

## 10. 上线前检查清单

- [ ] `JWT_SECRET` 已换成随机强密钥（不是示例值）
- [ ] 演示账号密码已修改或删除
- [ ] `llm-service` 的端口映射仍是 `127.0.0.1`，没有暴露到网卡
- [ ] 若要 Java 与 Python 分机部署：**先给分析服务加鉴权**（当前无鉴权，只靠回环保护）
- [ ] 数据库已做备份策略（迁移不可回滚，Flyway 社区版没有 undo）
- [ ] 前端 `npm run build` 产物已部署，不再用 `npm run dev`
